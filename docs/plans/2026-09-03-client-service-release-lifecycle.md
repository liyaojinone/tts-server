# BoboVox Client 与 BoboGenServer 的版本与分发机制

## 目标

`BoboGenServer` 是客户端之外的独立本地模型服务。客户端第一次安装时不预装它，
需要通过客户端的用户界面下载并安装；安装完成后，客户端通过 HTTP 接口使用它。

客户端和 `BoboGenServer` 可以分别安装、分别更新。客户端不把模型源码、Python
环境或模型权重打包进自己，而是提供安装入口和一层稳定的 HTTP API 对接。

开发者需要维护客户端与服务端的版本关系，但普通用户不需要理解这两个项目的
内部名称、仓库地址或版本匹配规则。用户看到的只是一个统一的“安装 / 更新模型
服务”流程。

## 核心规则

1. `BoboGenServer` 按稳定版本发布，不跟随 GitHub `main` 分支实时变化。
2. 客户端和 `BoboGenServer` 默认独立更新；客户端升级不等于服务升级，服务升级
   也不等于客户端升级。
3. 两边只通过稳定的 BoboGen HTTP API 协议对齐。只要 API 契约没有变化，客户端
   和服务就可以分别更新、分别运行。
4. 模型源码、模型环境和模型权重在每个服务发布版本中都有明确的版本记录。
5. 模型版本在当前服务版本内锁定；模型不会因为启动或联网而自行更新。
6. 新的服务版本可能继续使用原来的模型版本，也可能携带新的模型版本和权重。
   这由发布清单明确写出，不能由安装程序临时猜测。
7. 安装或更新失败时，旧的可用版本必须保留，不能把用户现有环境更新成半成品。

## 开发端维护版本关系，用户端只看到一个入口

开发者需要维护两层关系，但它们不是两套互相独立的兼容体系：

- 客户端 ↔ 服务：只维护 API 协议是否对齐；
- 服务 ↔ 模型：由服务发布清单锁定源码、环境和权重。

客户端和服务的生命周期可以不同，关系如下：

```text
客户端版本 ──(稳定 API 协议)── 服务版本 ──(发布清单)── 模型资源版本
```

示例：

```json
{
  "client_version": "1.4.0",
  "client_api_version": "v1",
  "service_version": "0.5.0",
  "service_api_version": "v1",
  "models": {
    "cosyvoice2": {
      "source_revision": "固定的上游版本",
      "environment_revision": "固定的环境版本",
      "weights_revision": "固定的权重版本"
    },
    "f5_tts": {
      "source_revision": "固定的上游版本",
      "environment_revision": "固定的环境版本",
      "weights_revision": "固定的权重版本"
    }
  }
}
```

这里的“锁定”不是说模型永远不能更新，而是说：**安装了某个服务版本后，模型
版本由该服务版本的清单确定，不允许安装程序随意拉取最新模型。**

## 用户看到的版本行为

| 用户状态 | 实际行为 |
|---|---|
| 第一次安装客户端 | 客户端发现本地没有模型服务，提供“安装模型服务”入口 |
| 旧客户端不升级 | 不触发服务更新，继续使用与它配套的旧服务和旧模型，功能保持可用 |
| 客户端升级 | 只更新客户端；如果现有服务仍满足 API 协议，不更新服务 |
| 服务版本更新 | 可以单独更新；按新服务发布清单检查模型源码、环境和权重 |
| 客户端 API 发生变化 | 只有现有服务不支持新 API 时，才提示需要更新服务 |
| 新服务仍使用旧模型 | 只更新服务代码，不重新下载权重 |
| 新服务带来新模型版本 | 服务更新流程一起下载并检测新权重 |
| 安装或更新失败 | 保留旧版本，显示失败原因和控制台日志 |

服务更新时模型大概率会随发布清单一起更新并重新下载权重；如果只是极少数的
服务代码修复且模型清单没有变化，则不需要重复下载权重。两种情况都由发布清单
决定，不能由客户端自行推断。客户端升级本身不触发这一步。

## 客户端如何接入模型服务

客户端只嵌入“入口、启动和 API 连接”，不嵌入模型源码、Python 环境或模型权重。
服务端的“模型服务”页面可以独立用浏览器打开，也可以由客户端通过本地 HTTP
地址嵌入或打开；普通用户不需要知道服务端内部仓库名称。

客户端的正常流程是：

```text
客户端启动
  ↓
检查本地模型服务是否存在并读取 API 版本
  ↓
没有服务：显示“安装模型服务”
  ↓
下载指定服务版本并安装服务底座
  ↓
启动服务管理接口
  ↓
用户选择模型，按模型安装 / 导入源码、环境和权重
  ↓
服务端检测资源完整性
  ↓
客户端通过稳定 API 调用模型
```

服务已经安装时，客户端直接连接它，不重复下载。客户端更新时也只更新客户端
本身；只有 API 协议对不上，或用户主动选择更新模型服务时，才进入服务更新流程。

## 首次安装流程

网页不能在没有任何本地进程的情况下自行安装 Python 环境和服务，因此第一次
安装需要一个很小的启动器。启动器不是模型服务，也不是客户端业务逻辑，只负责
启动安装页面和执行底座安装任务。

```text
启动器
  ↓
下载指定版本的 BoboGenServer
  ↓
安装服务底座依赖
  ↓
启动“模型服务”页面
  ↓
读取发布清单
  ↓
下载 / 导入模型源码、专属环境和权重
  ↓
执行完整检测
  ↓
报告“已准备”或具体缺失项
```

`BoboGenServer` 的源码、各模型服务、模型源码、专属 Python 环境、权重和运行时
文件都必须位于它自己的根目录中。不得因为用户机器上碰巧存在 Conda、系统
Python 或其他项目缓存而报告安装成功。

## 更新流程

客户端更新和服务更新是两个独立流程：

```text
客户端更新：安装新客户端
  ↓
读取现有服务 API 版本
  ↓
协议兼容：继续使用现有服务
协议不兼容：提示更新服务
```

```text
服务更新：检查新服务版本
  ↓
读取新版本发布清单
  ↓
比较当前服务和模型资源
  ↓
暂存需要更新的服务代码与模型资源
  ↓
完成环境、权重、路径和版本检测
  ↓
检测成功后切换到新服务版本
  ↓
失败则继续使用旧版本
```

更新时必须保留用户的参考音频、音色配置、生成结果和其他业务数据。模型权重
可以按版本清单单独缓存，避免因为服务代码更新而重复下载没有变化的资源。

## 版本关系的最低约束

不建立复杂的兼容矩阵，只检查 API 契约和发布清单是否满足以下关系：

```text
当前客户端版本 ──(稳定 API 协议)── 当前服务版本
                                  └─(发布清单)── 模型源码、环境和权重版本
```

因此：

- 新客户端不应无条件强制更新服务；
- 只要 API 协议保持兼容，客户端和服务可以分别更新；
- API 发生不兼容变化时，客户端必须明确提示服务更新要求；
- 服务更新不能静默替换模型版本；
- 模型资源不完整时，页面必须显示缺失项，而不是回退到用户电脑上的其他环境；
- 同一个安装记录中只能有一个当前生效的服务版本和每个模型的当前锁定版本。

## 页面职责

“模型服务”页面只需要让用户完成以下事情：

- 查看当前服务版本和运行状态；
- 查看模型资源是否完整；
- 安装或更新模型服务；
- 下载、导入或修复某个模型的资源；
- 查看安装日志和失败原因。

页面不向普通用户暴露 `BoboGenServer` 这个内部仓库名称，也不要求用户手动执行
Git、Conda、pip 或模型启动命令。

## 当前实现状态

当前服务端页面已经具备模型目录、文件检测和 Gateway 控制台日志展示能力。模型
列表的“下载”和“修复”已经接入后台资源任务：任务按固定清单串行执行，源码仓库
按已锁定 revision 校验，模型资源按官方 Hugging Face/ModelScope 地址和清单中的
固定 revision 补齐，完成后
重新检测缺失路径并把结果写入控制台。已有源码不会自动 pull 或覆盖，任务也不会
启动模型进程。检测会把 0 字节文件和空目录视为缺失；源码下载先落在临时目录，
只有校验成功后才切换到正式目录，网络中断后可以直接重试。

当前仍明确不在本页自动完成的事项：模型服务的 GPU 运行进程启动/停止、服务专属
Python 依赖的全量安装，以及需要 Hugging Face 授权或 ModelScope 工具而当前环境
尚未具备时的授权准备。这些操作必须在对应服务的官方安装环境内进行；页面会显示
具体失败原因，不会把缺少环境伪装成“已准备”。
